# AI Performance & Lifecycle Review Pack: Протокол аудита фоновой работы и жизненного цикла плагинов

**Документ:** `prepared-public/ai/packs/performance-review.md`
**Назначение:** Формализованный протокол и методическое руководство для AI-агентов (Auditor Worker, Supervisor Controller) при оценке производительности, архитектуры фоновой активности и жизненного цикла виджетов Quickshell / Omarchy Quattro.
**Источники данных:** `README.md`, `reports/DEEP_RISK_AND_ARCHITECTURE_ANALYSIS.md`, `reports/FINAL_REPORT.md`, `AGENTS.md`.
**Статус:** Нормативный протокол аудита (Audit Review Pack).

---

## 1. Цели и границы применимости

Протокол предназначен для автоматизированного или полуавтоматизированного анализа кода плагинов, написанных на QML, JavaScript, Python и Shell, функционирующих в среде рабочего стола Omarchy Quattro на базе Quickshell.

### Ключевой контекст среды выполнения
1. **Единый процесс (`Single-Process Model`):** Все плагины загружаются и выполняются внутри единого долгоживущего процесса `omarchy-shell` без изоляции памяти.
2. **Влияние на общую стабильность:** Зависание, блокирующий системный вызов или утечка ресурсов в одном плагине деградируют работу всей графической оболочки (панель, уведомления, меню, блокировщик экрана).
3. **Отсутствие эвристических домыслов:** Статический анализ исходного кода выявляет структурные паттерны, частоту вызовов и архитектурные контракты, но не подменяет натурные тесты.

## 2. Методологический рубеж: `runtime-measurement-required`

> **КРИТИЧЕСКОЕ ТРЕБОВАНИЕ К АГЕНТАМ-РЕВЬЮЕРАМ:**
> **Запрещено утверждать измеренное энергопотребление или точный разряд батареи на основании статического анализа кода.**
> Наличие таймера с малым интервалом или компонента `Process` указывает на **частоту пробуждений (wake-up frequency)** или **интенсивность порождения процессов (fork-exec rate)**, но **НЕ является измерением энергопотребления (мВт, Джоули, % заряда батареи в час, C-state residency)**.

### 2.1. Разделение областей наблюдаемости

| Параметр | Статический анализ кода (Данный протокол) | Требует натурных измерений (`runtime-measurement-required`) |
| :--- | :--- | :--- |
| **Интервалы и таймеры** | Номинальный `interval`, флаг `repeat`, предикаты `running` | Реальное отклонение интервалов (timer drift, jitter), частота таймерных прерываний ядра |
| **Порождение процессов** | Количество блоков `Process`, пути исполняемых файлов, конкатенация | Фактическая частота вызовов `fork()/exec()`, потребление CPU дочерними процессами |
| **Блокировки UI** | Наличие синхронных скриптов, циклов, тяжелых операций в QML | Длительность задержек кадра (frame drop), отзывчивость Wayland event loop |
| **Потребление памяти** | Модели владения QML (parent-child), утечки в JS-массивах | RSS/PSS процесса `omarchy-shell`, фрагментация кучи V8/QJSEngine |
| **Энергия и батарея** | Архитектурная классификация паттерна (см. раздел 3) | **Энергопотребление в ваттах, пробуждения процессора (`powertop`), срыв энергосберегающих состояний (`turbostat`, package C-states), скорость разряда (`/sys/class/power_supply/BAT*`)** |

### 2.2. Обязательный протокольный маркер `runtime-measurement-required`

Если агент в отчете описывает потенциальное негативное влияние на батарею или процессор, он **обязан**:
1. Формулировать вывод строго в терминах наблюдаемых сущностей: *«недросселированный таймер 50 мс в фоне создает непрерывный поток пробуждений event loop»*, а не *«плагин сажает батарею на 15% в час»*.
2. При необходимости квантификации физического расхода ресурсов помечать вывод статусом `[runtime-measurement-required]`.
3. Для снятия статуса `[runtime-measurement-required]` требуется проведение контролируемого теста:
   - Снятие профиля `powertop --csv` на фиксированном интервале (не менее 300 сек);
   - Замер состояний процессора через `turbostat --interval 5` (оценка выхода из C6/C8/C10);
   - Снятие метрик через Linux RAPL (`/sys/class/powercap/intel-rapl/` или `energy-pkg` в `perf stat`);
   - Фиксация базового потребления оболочки без плагина vs с активированным плагином при закрытой и открытой панели.

## 3. Таксономия механизмов фоновой работы и жизненного цикла

Агент обязан строго различать **7 базовых механизмов** при аудите компонентов QML/Quickshell. Подмена одного механизма другим (например, классификация дебаунсера как недросселированного таймера) является грубой ошибкой аудита.

```

│              ТАКСОНОМИЯ АРХИТЕКТУРНЫХ МЕХАНИЗМОВ QUICKSHELL / OMARCHY                  │
├──────────────────────────┬─────────────────────────────┬───────────────────────────────┤
│ Периодические таймеры    │ Событийные оптимизаторы     │ Системные шины и VFS          │
├──────────────────────────┼─────────────────────────────┼───────────────────────────────┤
│ • 1. Repeating Timer     │ • 2. One-Shot Debounce      │ • 5. Persistent Stream        │

│                          │                             │ • 7. Direct FileView          │
└──────────────────────────┴─────────────────────────────┴───────────────────────────────┘

### Механизм 1: Repeating Timer (Периодический таймер)

* **Синтаксический маркер:** `Timer { repeat: true; running: ...; interval: ... }`.
* **Архитектурное назначение:** Регулярное циклическое обновление данных по расписанию.
* **Критерии анализа:**
  - `interval < 1000`: Высокая частота (субсекундный опрос). При отсутствии строгой привязки к анимации или открытому интерфейсу является критическим архитектурным дефектом (постоянные пробуждения планировщика ОС).
  - `1000 <= interval < 10000`: Мультисекундный опрос (1–10 с). Допустим для интерактивных панелей, но нежелателен для постоянной фоновой работы.
  - `interval >= 10000`: Редкий опрос (от 10 с и выше). Стандартный умеренный фон для виджетов статуса (погода, проверка почты).
* **Что проверять в коде:** Что именно вызывается в `onTriggered`? Если внутри вызывается `Process.running = true` или shell-команда — это порождает постоянный fork-exec цикл.
* **Ошибочный вывод (Anti-pattern аудита):** Объявлять любой периодический таймер «утечкой батареи» без проверки интервала и выполняемого тела.

---

### Механизм 2: One-Shot Debounce (Одноразовый дебаунсер)

* **Синтаксический маркер:** `Timer { repeat: false; interval: <число>; onTriggered: ... }`.
* **Архитектурное назначение:**
  - Коалесценция (coalescing) всплесков пользовательского ввода (перемещение слайдера громкости/яркости, ввод текста в поле поиска).
  - Задержка стабилизации (settlement timer) после изменения системного состояния перед контрольным считыванием (например, ожидание раскрутки кулера 700 мс).
* **Поведение в рантайме:**
  - Запускается методом `.restart()` только по факту физического взаимодействия.
  - Срабатывает ровно один раз и переходит в неактивное состояние (`running: false`).
  - После срабатывания таймер не планирует следующие циклические события. Фактическая загрузка CPU вне этого механизма требует runtime-измерения.
* **Пример из кодовой базы (`moerdowo_omarchy-mac-fan-control`):**
  ```qml
  Timer {
    id: percentDebounce
    interval: 180
    repeat: false
    onTriggered: {
      root.holdingPercent = false
      root.setPercent(root.percent)
    }
  }
  ```
* **Ошибочный вывод (Anti-pattern аудита):** Регулярно встречающаяся ошибка ранних эвристических сканеров: маркировка таймера `interval: 180` как «критической угрозы батарее» из-за того, что `180 < 1000`, игнорируя свойство `repeat: false`.

---

### Механизм 3: Visibility Gating (Шлюзование по видимости UI)

* **Синтаксический маркер:** Привязка активности таймера или процесса к состоянию видимости графического элемента:
  ```qml
  Timer {
    interval: 1000
    repeat: true
    running: root.opened && !root.sleeping
  }
  ```
* **Архитектурное назначение:** Полная остановка фоновой активности при закрытом поп-апе, скрытом окне или свернутой панели.
* **Критерии анализа:**
  - Для выпадающих меню, расширенных настроек и детализированных окон видимость (`opened`, `visible`, `revealed`) **обязана** останавливать периодический опрос.
  - Может исключить именно этот периодический триггер в закрытом состоянии. Нулевая суммарная нагрузка не гарантируется: проверьте другие таймеры, процессы, bindings и runtime-метрики.
* **Исключения:** Виджеты, отображающие текущее состояние непосредственно на панели задач (tray/bar items), объективно требуют периодического обновления базовых метрик даже при закрытом детальном поп-апе (см. Dual Cadence).

---

### Механизм 4: Dual Cadence (Адаптивный двухрежимный опрос)

* **Синтаксический маркер:** Динамическое тернарное или условное вычисление интервала таймера в зависимости от фокуса или видимости:
  ```qml
  Timer {
    interval: root.opened ? 2000 : 20000
    running: true
    repeat: true
    onTriggered: root.refresh()
  }
  ```
* **Архитектурное назначение:** Компромисс между интерактивностью панели и сохранением ресурсов в покое:
  - **Active Cadence (Панель открыта):** Быстрый опрос (1–2 с) для плавного отображения изменений параметров (например, температура CPU, обороты кулера, уровень громкости).
  - **Relaxed Cadence (Фоновый режим):** Замедленный опрос (20–300 с) для поддержания актуальности индикатора на главной панели без деградации ресурсов.
* **Математика снижения нагрузки (пример `moerdowo.fan`):**
  - При 2 сек постоянного опроса: $1\,800$ вызовов процесса в час.
  - В фоновом режиме 20 сек: $180$ вызовов в час (снижение активности на 90%).
  - В режиме `moerdowo.mayar` (20 с открыт / 300 с закрыт): фоновое число вызовов снижается до $12$ в час.
* **Ошибочный вывод (Anti-pattern аудита):** Оценка таймера по его минимальному интервалу (например, фиксация "2000 ms polling" без учета перехода на 20000 ms).

---

### Механизм 5: Persistent Stream (Долгоживущий потоковый воркер)

* **Синтаксический маркер:**
  ```qml
  Process {
    id: worker
    command: [root.helperPath, "listen"]
    running: true
    stdinEnabled: true
    stdout: SplitParser {
      onRead: function(line) { root.handleUpdate(line) }
    }
  }
  ```
* **Архитектурное назначение:** Замена сотен периодических запусков CLI-утилит одним долгоживущим вспомогательным процессом (helper/daemon), общающимся через `stdout` (newline-delimited JSON) и `stdin`.
* **Преимущества перед Polling:**
  - Исключает накладные расходы ядра на постоянный цикл `fork() -> execve() -> dynamic link -> exit()`.
  - Модель push-уведомлений: процесс спит в системном вызове (`poll`/`epoll`/`read`) и пробуждает QML только при реальном событии (подключение Bluetooth-устройства, смена трека, изменение сетевого интерфейса).
* **Критерии проверки агентом:**
  1. Наличие обработки аварийного завершения: `onExited` обязан выставлять статус ошибки и использовать дебаунс-таймер для повторного подключения (backoff), предотвращая tight crash loop.
  2. Безопасность буфера ввода: использование `SplitParser` предотвращает фрагментацию строковых пакетов и переполнение памяти.

---

### Механизм 6: Reactive Service (Встроенный реактивный C++ сервис)

* **Синтаксический маркер:** Использование синглтонов `Quickshell.Services.*`:
  - `Quickshell.Services.Pipewire` (управление аудио и узлами звукового сервера);
  - `Quickshell.Services.Mpris` (управление медиаплеерами через D-Bus);
  - `Quickshell.Hyprland` (мониторинг рабочих столов, окон и активных мониторов через сокет IPC).
* **Архитектурное назначение:** Наивысший стандарт качества и производительности в экосистеме Omarchy.
* **Характеристики:**
  - **0 порождаемых внешних процессов (`Process {}` = 0).**
  - **0 периодических таймеров (`Timer {}` = 0).**
  - Прямое взаимодействие через shared library или сокет IPC в рамках основного цикла событий Qt.
  - Событийная модель избегает периодического опроса; задержка и CPU overhead требуют runtime-измерения на целевом хосте.

---

### Механизм 7: Direct FileView (Прямое чтение виртуальной ФС ядра)

* **Синтаксический маркер:**
  ```qml
  import Quickshell.Io
  FileView {
    path: "/proc/meminfo"
    // прямое чтение буфера в C++
  }
  ```
* **Архитектурное назначение:** Считывание системной телеметрии ядра Linux (`/proc/`, `/sys/`) без запуска утилит `cat`, `free`, `top`, `awk` или скриптов оболочки.
* **Характеристики:**
  - Чтение выполняется встроенным C++ кодом Quickshell через системный вызов `read()` из памяти ядра.
  - Полностью исключает запуск командного интерпретатора `sh` / `bash` и порождение подпроцессов.
* **Критерии проверки агентом:** Проверять частоту перечитывания `FileView` и корректность обработки ситуаций, когда файл в `/sys/` временно недоступен (горячее отключение оборудования).

## 4. Пошаговый протокол анализа жизненного цикла для AI-агента

При выполнении аудита плагина агент обязан следовать строгому пятифазному алгоритму:

```
┌────────────────────────────────────────────────────────────────────────┐
│               АЛГОРИТМ РАБОТЫ АГЕНТА-РЕВЬЮЕРА (5 ФАЗ)                  │
├────────────────────────────────────────────────────────────────────────┤
│ 1. Инвентаризация     → Поиск всех Timer {}, Process {}, FileView      │
│ 2. Декомпозиция       → Классификация по 7 механизмам таксономии       │
│ 3. Проверка барьеров  → Анализ repeat, opened, visibility, crash loop  │
│ 4. Анализ нагрузки    → Оценка частоты пробуждений и fork-exec         │
│ 5. Фиксация вердикта  → Формирование Anchors + граница измерений       │
└────────────────────────────────────────────────────────────────────────┘
```

### Фаза 1: Инвентаризация сущностей
1. Открыть и прочитать каждый файл плагина (`.qml`, `.js`, `.sh`, `.py`) через инструмент `read`.
2. Зафиксировать все объявления:
   - `Timer` (интервал, признак повторения, условие запуска);
   - `Process` (команда, флаг фонового запуска, наличие потокового парсера);
   - Обращения к сервисам `Quickshell.Services.*` и объектам `FileView`.

### Фаза 2: Классификация и дифференциация механизмов
Для каждого найденного компонента сопоставить его с одним из 7 механизмов:
- Если `Timer` и `repeat: false` $\rightarrow$ **One-Shot Debounce**. Проверить контекст вызова (`restart()`).
- Если `Timer` и `repeat: true`:
  - Проверить свойство `interval`: статическое число или тернарное выражение?
  - Если тернарное (`opened ? A : B`) $\rightarrow$ **Dual Cadence**.
  - Если условие `running` содержит `root.opened` или `visible` $\rightarrow$ **Visibility Gating**.
  - Если `running: true` постоянно и `repeat: true` $\rightarrow$ **Repeating Timer**.
- Если `Process` запущен постоянно с `SplitParser` $\rightarrow$ **Persistent Stream**.
- Если взаимодействие с внешним миром идет без `Process` через API Quickshell $\rightarrow$ **Reactive Service**.
- Если считывается `/proc` через `FileView` $\rightarrow$ **Direct FileView**.

### Фаза 3: Проверка защитных барьеров и устойчивости
- **Проверка отсутствия Tight Loop:** Если таймер или процесс перезапускаются в обработчиках ошибок (`onError`, `onExited`), присутствует ли задержка (backoff timer не менее 1–2 с)?
- **Проверка спама процессов:** Не запускается ли новый экземпляр `Process` до завершения предыдущего (`waitForEnd: true` или проверка `running == false`)?
- **Проверка фоновой изоляции:** Отключаются ли ресурсоемкие анимации (`FrameAnimation`, `NumberAnimation`) при сокрытии панели?

### Фаза 4: Оценка вычислительной нагрузки (Без утверждений об энергии!)
- Оценить номинальную частоту пробуждений (wakeups per second / minute).
- Оценить частоту порождения процессов (fork-exec per minute / hour).
- **Сформулировать границы:** Явно указать, что оценка базируется на частотных характеристиках кода, а физическое энергопотребление относится к `runtime-measurement-required`.

### Фаза 5: Формирование вердикта и якорей (Evidence Anchors)
Каждое существенное наблюдение (дефект или защитный паттерн) обязано сопровождаться точным якорем:
- `file`: Относительный путь к файлу.
- `line`: Номер строки.
- `snippet`: Точная посимвольная цитата из исходного кода.
- `mechanism`: Один из 7 механизмов таксономии.
- `assessment`: Обоснование риска без спекулятивных утверждений о ваттах или процентах разряда.

## 5. Матрица вердиктов и критерии классификации

| Вердикт | Критерии в разрезе жизненного цикла и фоновой работы |
| :--- | :--- |
| **`pass`** | - Применяются реактивные сервисы (`Reactive Service`), `FileView` или потоковые воркеры (`Persistent Stream`).<br>- Все периодические таймеры снабжены `Visibility Gating` либо работают в режиме `Dual Cadence` с фоновым интервалом $\ge 20$ с.<br>- Субсекундные таймеры являются исключительно `One-Shot Debounce` (`repeat: false`).<br>- Отсутствуют неконтролируемые циклы перезапуска при сбоях. |
| **`warning`** | - Присутствует циклический `Repeating Timer` с интервалом от 1 до 10 секунд без шлюзования по видимости (`Visibility Gating`), но выполняющий легкие операции (чтение переменной, не порождающее shell-процесс).<br>- Фоновый интервал в `Dual Cadence` составляет менее 10 секунд.<br>- Отсутствует экспоненциальный backoff при падении потокового демона (перезапуск через фиксированные 1–2 сек). |
| **`broken`** | - Синтаксические ошибки в объявлении таймеров или процессов.<br>- Бесконечный tight loop перезапуска упавшего процесса с нулевой задержкой (`onExited: running = true`), создающий риск насыщения потока событий (unthrottled spin loop; точная нагрузка на CPU требует runtime-измерения).<br>- Обращение к несуществующим методам жизненного цикла. |
| **`suspicious`** | - Высокочастотный недросселированный опрос ядра или оборудования с правами повышенных привилегий (например, `modprobe` или запись в sysfs через `pkexec/sudo` каждые 30 секунд в фоновом цикле).<br>- Скрытый запуск майнеров, сборщиков телеметрии или сетевых демонов под видом дебаунсеров. |

## 6. Чек-лист для AI-агента перед публикацией отчета

Перед тем как выставить вердикт по разделу `lifecycle_battery`, агент обязан ответить на контрольные вопросы:

- [ ] **1. Проверка `repeat: false`:** Все ли таймеры с малым интервалом (`interval < 1000`) проверены на наличие свойства `repeat: false`? Не назван ли дебаунсер циклическим таймером?
- [ ] **2. Проверка тернарных интервалов:** Проверен ли код `interval` на наличие условий переключения режимов (Dual Cadence)?
- [ ] **3. Проверка видимости панели:** Привязано ли свойство `running` периодического таймера к `root.opened` / `root.visible`?
- [ ] **4. Проверка природы потока:** Если плагин держит открытый процесс, использует ли он `SplitParser` (событийный стрим) или перезапускает утилиту в цикле?
- [ ] **5. Соблюдение рубежа измерений:** Нет ли в тексте отчета прямых утверждений вида «плагин тратит 3 Ватта», «сажает батарею за 2 часа»? Содержит ли отчет отметку `runtime-measurement-required` при обсуждении физического энергопотребления?
- [ ] **6. Точность цитат:** Проверены ли номера строк и совпадение текста сниппетов для всех якорей в массиве `anchors`?

## 7. Эталонный пример секции отчета агента

Пример корректно оформленного фрагмента анализа плагина:

```markdown
### Анализ жизненного цикла и фоновой активности: `moerdowo_omarchy-mac-fan-control`

* **Классификация механизмов:**
  - `Panel.qml:165-170` — **Dual Cadence Polling**:
    ```qml
    interval: root.opened ? 2000 : 20000
    running: true
    repeat: true
    ```
    *Анализ:* При открытой панели опрос датчиков производится каждые 2 сек. При скрытой панели интервал увеличивается до 20 сек, снижая число вызовов вспомогательного бинарника на 90% (со 1800 до 180 в час).
  - `Panel.qml:195-201` — **One-Shot Debounce**:
    ```qml
    id: percentDebounce
    interval: 180
    repeat: false
    ```
    *Анализ:* Интервал 180 мс служит для сглаживания перемещения ползунка пользователем. Благодаря `repeat: false` этот таймер не создаёт самостоятельного циклического опроса; фактическая фоновая загрузка всего плагина требует runtime-измерения.
* **Физическое энергопотребление:**
  - Статус: `[runtime-measurement-required]`.
  - Статический код демонстрирует корректную архитектуру троттлинга. Точное влияние фонового опроса (180 вызовов/час) на время автономной работы ноутбука и C-states процессора требует аппаратного замера через `turbostat` и `/sys/class/power_supply/BAT0/`.
* **Вердикт секции:** `pass`.
```
